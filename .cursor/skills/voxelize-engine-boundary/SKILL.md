# Engine Boundary

Voxelize is the engine; games are consumers that use and extend it. The engine must not know what blocks, items, creatures or worlds exist, what a game calls things, or where a consumer's files live. The rule is `.cursor/rules/engine-boundary.mdc`; this is the workflow.

## The gate

```bash
node scripts/engine-boundary/check.mjs          # this repo, against the hashed denylist
node --test scripts/engine-boundary/check.test.mjs
```

It scans every tracked and untracked file (file names included) and reports `path:line:col "text"` with the reason. Rules:

- **term**: a consumer's block, item, creature, world or game term, matched as a whole phrase after splitting identifiers, so `QuuxWidget`, `quux_widget` and `Quux Widget` are one phrase. The vocabulary is `denylist.json`: digests generated by each consumer from its registries, so this repo never contains the names it forbids. The banned game name is one of the digests.
- **block-name-literal**: engine source (not tests, examples or docs) branching on a literal block name.
- **path-escape**: a relative path that resolves outside this repo.
- **consumer-path** / **consumer-import**: a root-relative path into a consumer's tree, or an import of its alias or package.

A consumer runs the same gate in its own CI with `--vocabulary <plain.json>`, replacing its hashed groups with its live names, so a name added downstream is off limits immediately.

## Fixing a hit

Pick one, in this order:

1. **Neutralize** a fixture or comment: a game's creature kind in a test becomes `walker`, a game's vehicle in a comment becomes "a vehicle". Tests prove the same thing with neutral names.
2. **Move it to the consumer** when only one game needs it.
3. **Make an extension point** when the engine needs the capability but not the specifics:
   - a *config* field or options object with a neutral default (water optics, budgets, env var names → `AGENT_CACHE_DIR`, `VOXELIZE_PERF_LOG`);
   - a *hook* the consumer registers (a filter callback like `waterOpticsFluidFilter`, a pairing rule for linked blocks);
   - a *registry* the consumer fills (block profiles, arena method names, spawn payload fields).

The consumer then supplies the specifics, and its behaviour does not change: keep its old names at its own edge (its launcher maps its env vars; its shim keeps its import paths).

## Excuses and debt

`excuses.json` holds legitimate hits: attribution (README showcase, the docs landing page), design notes recording which consumer drove a design, a module's own neutrality test. Each entry names a path (a trailing `/` covers a directory), the terms or the rule, and a reason. An entry that stops matching fails the gate, so the list only describes what is really there.

A hit you cannot fix yet — it sits inside another workstream's in-flight hunk, or renaming it would break a live measurement — gets an excuse with `until`, naming the work that removes it. Every run prints the debt list.

## Regenerating the denylist

The consumer owns it. In the production consumer: `pnpm boundary:denylist` rewrites `scripts/engine-boundary/denylist.json` here from its registries, minus its generic-terms list (words engine code uses for their plain meaning). The consumer's gate reports how far the committed digests trail its registries; land a regeneration with the next engine commit.

## The periodic pass

The gate catches names. A pass looks for what names cannot show:

- constants tuned to one game's content (colours, fog, sky, weather, budgets) living as frozen module constants instead of overridable defaults;
- engine logic that only one game exercises (a block pairing, a special-cased entity kind, a hard-coded method or env var name);
- agent-package surface that mirrors one host (bridge snapshot fields for one game's mechanics, default method maps);
- generic utilities the consumer wrote that belong in the engine (budgeted drains, instancing, texel painters), and engine utilities the consumer duplicates;
- `until` excuses whose workstream has landed, and generic-term entries that have become real names.

Report it as a table: file:line, what, and the action (moved, generalized, kept with reason, or after which workstream).
